Absorbed from the former `safe-file-operations` skill (deleted 2026-07-23 in favour of this memory). Applies whenever reading, editing, or creating a file on disk.

**Reading — inspect before read.** Never dump a file blindly. First check size/length (`ls -lh <file>` and `wc -l <file>`), decide which portion is actually needed, then read a line range with the agent's read tool (Read/view), not `cat`. For large files, `grep -n <pattern> <file>` to locate regions of interest, then read just those ranges.

**Editing — Edit and Write are the only tools I may use to change a file's content on my own authority.** This is an allowlist, not a blocklist: if a change to a file's bytes does not go through the agent's Edit (str_replace) or Write (create_file) tool, I may not do it without asking first, no matter which program would do the writing. Naming offenders is only illustration — `sed -i`, `awk -i inplace`, `perl -pi`, `python -c` / `python - <<EOF`, `ruby -i`, `node -e`, `cat > file`, `cat >> file`, `tee`, `printf >`, heredocs, `ed`/`ex`, applying a hand-written diff with `patch`/`git apply` — and a program being absent from this list does not make it allowed. Swapping the language (python → ruby → shell → anything) does not create an exception; the question is never "is this tool banned?" but "is this Edit or Write?". Bash exists for running programs (build, test, git, ls, grep, rg) and for reading; it never authors file content on its own. This applies to code, docs, config, and memory files alike, and in the agents repo (`~/agents`, symlinked to `~/.claude`) exactly as anywhere else. Such edits are not reviewable and a single typo corrupts the file. Edit for targeted surgical changes, Write for brand-new files or intentional full rewrites.

**Non-Edit/Write mutations — ask first, every single time.** Bulk changes (a rename across dozens of files, a mechanical rewrite a script does better) can legitimately call for `sed -i`, a python script, `sudo cp` of Write-authored content into a root-owned path, or similar. That is allowed only after asking the user and receiving approval for that specific operation, whatever the circumstances — mid-task, autonomous run, "obvious" case, time pressure, none of it waives the ask. The request must show what will run and what it touches: the exact command/script, the file list (from `grep -l`/`rg -l`), and why per-match Edit is impractical. Then stop and wait; do not run it "provisionally". One approval covers one operation: a second bulk edit later in the same session needs its own ask (same pattern as [[feedback_push_only_when_asked]]). The only exception is an explicit waiver from the user — "물어보지 말고 해", "no need to ask", "just script it" — which covers the scope they named and nothing beyond it. This is one of the genuine forks where asking is required even under [[feedback_act_dont_over_ask]].

**Regex / multi-match edits — locate, then edit one by one.** Don't chain a regex into `sed -i`. (1) `grep -nE '<pattern>' <files>` to confirm it catches exactly what's intended and nothing else; (2) review the match list, refine the pattern if any false positive appears; (3) apply each confirmed match individually with Edit (`replace_all` per token/file, or enough surrounding context to make each replacement unique). `sed`/`awk`/`grep` are for reading and locating only.

**When Edit fails — fix the match, don't switch tools.** A failed Edit ("old_string not found" / "not unique") means my anchor text is wrong, not that Edit is the wrong tool. Typical causes: line-number prefixes copied from Read output, tabs vs spaces, trailing whitespace, smart quotes or other unicode, or a stale view because an earlier edit already changed the region. Recovery: (1) Read the exact lines again; (2) copy the anchor verbatim from that fresh read; (3) retry Edit, widening the context or using `replace_all` until it is unique. If the change genuinely can't be expressed as an Edit, Read the whole file and Write it in full. The recovery is another Edit or a Write; reaching for any other program (python, sed, perl, ruby, a shell heredoc, whatever is at hand) to "just patch it" is never something I decide alone. If I genuinely believe a script is the right tool, that is a question for the user, asked as described above, not a fallback.

**Why:** 2026-07-22, on a project-wide `orbis` → `mangos` rename I wrote a `rename.sed` and ran `sed -i` over 14 files. It verified clean, but the user objected — they want every change individually visible/auditable in the tool stream, not hidden inside one opaque sed run. A real over-replacement (an ORBIS-side filename `seed/orbis-install.sh` that had to stay) only surfaced because we diffed afterwards; per-match Edit would have caught it at write time. Again 2026-09-07: after Edit calls failed on files in the agents repo, I fell back to python/sed scripts to apply the change. The user objected sharply — this memory already banned sed/awk/perl, but python wasn't named and the "Edit failed → script" path wasn't covered, so the fallback slipped through. The user then pointed out that naming python just invites the next fallback (ruby, shell, …), so the rule is now stated as an allowlist — Edit/Write only — rather than a list of banned programs. Same day, a further refinement: bulk edits may sometimes genuinely be needed, so non-Edit/Write mutations are not banned outright but gated — ask the user and get approval for that specific operation every time, no exceptions, unless the user explicitly waives the ask.

**How to apply:** for any multi-file rename/refactor, grep to enumerate matches, then Edit each (replace_all per token per file) or Write full files — one inspectable diff per change. Bash is for reading, locating, and running programs (build/test/git); it does not author file content on my own authority. Before any Bash command, ask: does this change the bytes of a file I am authoring? If yes, it must be Edit/Write, or else I stop and ask the user for approval of that exact command and file list — every time, unless they explicitly waived the ask for this scope. On an Edit failure, re-Read and retry Edit; never route around it with another program without that approval. Coheres with [[feedback_minimal_comments_docs_separate]] and [[feedback_label_evidence_and_sources]] on keeping work auditable.
